우리가 캐싱 전략을 다시 설계한 이유

이하늘 buildnote.dev 2024년 11월 3일 읽는 데 약 6분

왜 기존 캐시가 무너졌나

지난 분기까지 우리는 TTL 고정형 캐시를 5분 단위로 돌려왔다. 문제는 트래픽이 몰리는 시간대에 캐시 적중률이 61.4%까지 떨어지면서 원본 DB가 그대로 노출됐다는 점이다. 장애 리포트를 열어보면 절반 이상이 이 구간에서 시작됐다.

캐시는 만병통치약이 아니다. 잘못 쓰면 버그를 캐싱하는 꼴이 된다.

새 전략: 계층형 무효화

키를 단일 레이어로 두지 않고, 요청 단위·사용자 단위·전역 단위 세 계층으로 나눴다. 이렇게 하면 한 사용자의 데이터가 바뀌어도 전역 캐시를 통째로 날릴 필요가 없다.

  • 요청 단위: 60초 TTL, 동일 파라미터 재요청만 흡수
  • 사용자 단위: 쓰기 발생 시 즉시 무효화
  • 전역 단위: 스키마 변경 등 드문 이벤트에서만 초기화
cache.key = `v2:${userId}:${resourceId}:${paramsHash}`

결과

적용 2주 뒤 적중률은 88.7%로 올라갔고, 야간 배치 시간대 DB 커넥션 풀 고갈 알림은 0건이었다. 무효화 로직이 늘어난 만큼 테스트 코드도 같이 늘었다는 점은 감수할 부분이다.
